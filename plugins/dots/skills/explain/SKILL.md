# Explain

Explain the named subject or, when none is named, the previous answer. Ask what
to explain only when neither is usable.

Start with the real situation, result, or decision. Write for an intelligent
adult who is new to the subject: keep the real mechanism and necessary terms,
define them when they matter, and add only the context needed to build the
smallest working mental model. Stop when the missing bridge is clear.

Use one concrete example, direct comparison, or compact visual when it makes the
mechanism clearer. Prefer round numbers. Add exact calculations only when they
are the point. An analogy may reinforce the mechanism after it is explained,
but never lead or replace it. For a failure or risk, begin with one verified
situation in which it occurs. If none is verified, say so.

If the conversation already supports the answer, explain it immediately. If the
previous answer did not land, re-pitch the missing concept rather than merely
shortening it. Research only when accuracy requires it.

Be specific. Say what it does, not how it feels. Prefer the plain word. Vary
rhythm. Short sentences. Then longer ones that take their time. Mix it up.

When research is needed, read only the sources required for accuracy. Separate
what they show from inference, and state any proof gap that changes the answer.
Use only the routes that apply:

- For a substantial or writing-heavy explanation, read the shared
  [writing style](../../references/writing-style.md).
- For a pull request, diff, or completed work, read
  [changes.md](references/changes.md).
- For code or system mechanics, architecture, a plan, or a multi-part concept,
  read [walkthroughs.md](references/walkthroughs.md).
- For intent, history, rationale, or rejected alternatives, read
  [reasons.md](references/reasons.md). When the question asks both how and why,
  explain the mechanics first and investigate intent only where mechanics do
  not answer it.
Explain tradeoffs when they aid understanding. Route requests to judge quality
or propose changes to the appropriate review skill; Explain itself does not
critique architecture.
